A WordPress update can pass on staging and still fail in production. Your payment provider may behave differently in live mode, a scheduled job may run only on production, or a cache may hide the problem while you test. Staging gives you somewhere to find problems before release. A tested backup gives you a way back when a problem slips through.

For a small team, both belong in the same routine. Before a change goes live, know which copy you can restore, who can restore it and what would happen to the orders, enquiries or edits that arrive after that copy was taken.

## 1. Decide how much you can lose

Pick a recovery point objective (RPO) and a recovery time objective (RTO) for each site. RPO is the maximum acceptable age of recovered data. RTO is the maximum acceptable time to restore a usable service. They are targets you set with the people who run the site.

A brochure site with occasional edits can often work with a different backup frequency from a store taking orders throughout the day. For example, if a store can tolerate at most one hour of lost orders, a nightly database backup alone cannot meet that target. A backup every hour is only a starting point. Confirm the backup completes, remains available and can be restored inside your outage window. Measure recovery from incident detection through to a working site, including the time it takes to obtain credentials and verify the restored service.

## 2. Keep a complete backup outside production

Capture the WordPress database and the matching files. The database contains posts, settings and other application records. Files include uploads, themes, plugins and configuration needed to rebuild. Document any pieces outside the backup, such as object storage, environment configuration and DNS. Keep credentials in your approved secret store and document how the recovery owner can obtain access.

Use 3-2-1 as a starting point. Keep three copies in total, including production, across two storage types or systems, with one copy off-site. An independent copy should remain reachable if the hosting account is locked or the primary storage is unavailable. Use separate credentials, limit deletion access and consider versioning or immutable retention where available. Check how the backup provider charges for storage, restores and data transfer before choosing a plan.

![Three copies across two storage systems, with one off-site copy.](/images/week6-backup-copies.png)

Write down the backup schedule, who checks alerts and how long each copy is retained. Retain enough history to recover from a fault discovered days after it started. Keep the pre-release snapshot long enough to cover your monitoring window. For South African teams with intermittent power or connectivity, use an automated backup destination that can run without somebody’s laptop online. Check for missed jobs after an interruption and make sure a second authorised person can recover the site.

## 3. Run a restore drill

Restore a recent backup into an isolated environment using the recovery instructions. Block real email, payments and production webhooks before allowing application traffic. Start the timer when the drill begins. Record which backup you used, its timestamp, how long the restore took and the checks that passed or failed.

Open the home page and a representative set of URLs. Sign in as an authorised tester, check media, and run the main conversion path using test credentials. On a store, check that product and order records are present and use a payment sandbox for checkout. For a membership site, test sign-in and permissions with seeded accounts. Confirm that WordPress can locate its uploads and that the restore did not point back to production databases or external services.

If the drill exceeds your RTO, record where the time went. Slow uploads, missing credentials and manual DNS steps all have different fixes. Run the drill again after a change in hosting, backup tooling or architecture. Give someone other than the person who wrote the instructions a turn at running it.

## 4. Rehearse the release on staging

Keep staging close enough to production to expose compatibility issues. Match PHP and WordPress versions, active plugins, theme, caching behaviour and any scheduled jobs relevant to the release. Gate staging behind authentication or a network restriction. Search-engine indexing settings are a supplementary control.

Test with synthetic or minimised data where possible. Backups and staging copies can contain personal information from orders, form entries and user accounts. Restrict access, encrypt stored copies and set retention and deletion rules. If an external provider processes the data on your behalf, include its role in your POPIA review. Section 19 addresses safeguards and section 21 addresses operator security measures.

![Staging safeguards include restricted access, test data and sandbox integrations.](/images/week6-staging-guardrails.png)

Deploy the exact versions you exercised on staging. For a plugin update, record the old and new versions and check whether it changes the database. Test the release as a visitor and as someone who operates the site. Keep a short list of critical paths in the release notes so the person doing the production checks can repeat them consistently.

## 5. Deploy with a rollback decision already written down

Before you start, take a fresh backup and record its timestamp. Assign one release owner and one person to make the rollback call if possible. Write down the symptoms that would trigger it, such as broken checkout, failed form delivery or an inaccessible admin area. Schedule the release while someone with the right access can respond.

Move only the planned changes. A staging database is usually older than production. Copying it over a live store can erase new orders, customer accounts and stock changes. Prefer targeted code or configuration changes and apply database migrations deliberately. Test business-critical journeys immediately after release, then monitor logs and reports for a defined period.

![Release checklist. Back up, rehearse, deploy, verify and monitor.](/images/week6-deploy-checklist.png)

### Choose the smallest safe rollback

If the change is code-only and the previous version is compatible with the current database, restore that version and recheck the affected journeys. If a migration changed the schema or data, follow the documented rollback procedure or use a tested forward fix. Before restoring a database, preserve a copy of the current state and identify what has changed since the recovery point. Pause writes where practical and agree how any new orders, submissions or edits will be reconciled. After recovery, verify the same critical paths and note the final recovery time and data gap.

## Frequently asked questions

### Is my host’s backup enough?

Check what it includes, whether you can export it, and how a restore works if you lose access to the hosting account. Keep an independent copy and test it.

### Should I back up before every plugin update?

Take a fresh recovery point before a planned change that could require rollback. Check whether the plugin updates database tables and whether the previous version can read the updated schema.

### Can I use the production database on staging?

Prefer synthetic or minimised data. If you need a production-derived copy, restrict access, sanitise it where practical, use test credentials and define when the copy will be deleted.

### How often should I test restores?

Set a recurring cadence based on how critical the site is, and repeat the drill after significant infrastructure or backup changes. Record elapsed time and check it against your RTO.
